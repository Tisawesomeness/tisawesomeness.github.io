This highly technical snapshot adds data-driven dispensers, Vulkan by default, and drastic changes to the networking protocol.

## Security Advisory

> [!CAUTION]
> A remote code execution [vulnerability](https://orca.security/resources/research/java4shell-critical-openjdk-base64-decoder-flaw-could-allow-unauthenticated-remote-code-execution/) was discovered in Java when using an [AVX-512 capable CPU](https://www.eatyourbytes.com/list-of-cpus-with-avx512/).
> 
> To patch the vulnerability, update Java to the following versions, or `-XX:+UnlockDiagnosticVMOptions -XX:-UseBASE64Intrinsics` to the JVM arguments:
> 
> | Release | Patched Version |
> | ------- | --------------- |
> | 8       | `8u513`         |
> | 11      | `11.0.33.1`     |
> | 17      | `17.0.21.1`     |
> | 21      | `21.0.13.1`     |
> | 25      | `25.0.5.1`      |
> | 27      | `27.0.1.1`      |
> 
> The vanilla launcher, Prism Launcher, Modrinth Launcher, and others have already applied mitigations.

## Phantoms

Phantoms now only damage players when their eye position has line of sight with the player's eye position, fixing {::bug:MC-310401}.

## Data Packs

### Entity Data

Pigs and Striders now save their speed boost from using a carrot or warped fungus on a stick, fixing {::bug:MC-313141}:

- Compound `item_based_steering`
	- Boolean `boosting`: Whether the mob is currently boosting from a carrot or warped fungus on a stick
	- Integer `boost_time`: Ticks spent boosting
	- Integer `boost_time_total`: Total ticks to spend boosting

### Dispense Behaviors

Ominous Item Spawners will use the selected item's first `shoot_projectile` dispense behavior to spawn the projectile.

## LAN Server

`key-rotation-period-seconds` is always the default, 60 seconds.

## Signaling API

### GET `getConfiguration`

When Minecraft starts, the client sends a `getConfiguration` request to the signaling service:

#### Request

- `x-mojangauth`: The Minecraft access token
- `Session-Id`: A random UUID generated once on startup
- `Request-Id`: A random UUID generated for each request

Example:

```
x-mojangauth: <token>
Session-Id: 87c025a5-8ab5-4c07-8188-2057dabf7ed1
Request-Id: e4a43120-687a-4b13-97e7-d175b0f4aae2
```

#### Response

- `result`
    - `signalingUri`: A base URI to a Minecraft signaling server
    - `pingFrequency`: A duration in `hh:mm:ss` format, must be at least one second

Example:

```json
{
  "result": {
    "signalingUri": "wss://signal-eastus2.franchise.minecraft-services.net",
    "pingFrequency": "00:05:00"
  }
}
```

### GET `connect`

Then, the client opens a websocket connection to the URL at the `connect` endpoint, with `{signalingUri}` replaced with `signalingUri` received from the `getConfiguration` endpoint.

For example, the client opens a websocket connection at `wss://signal-eastus2.franchise.minecraft-services.net/ws/v1.0/messaging/connect/java`.

#### Request

- `x-mojangauth`: The Minecraft access token
- `Session-Id`: A random UUID generated once on startup
- `Request-Id`: A random UUID generated for each request

Example:

```
x-mojangauth: <token>
Session-Id: 87c025a5-8ab5-4c07-8188-2057dabf7ed1
Request-Id: e4a43120-687a-4b13-97e7-d175b0f4aae2
```

## Signaling Protocol

Once the websocket connection is open, the client sends and receives signaling messages through the websocket using the [JSON-RPC 2.0](https://www.jsonrpc.org/specification) protocol.

### Reconnecting

If the client disconnects, or no pong is received within 15 seconds of a ping, the client will attempt to reconnect after a random delay, increasing after each failed attempt:

| Attempt | Delay         |
| ------- | ------------- |
| 1       | 0.5-1 seconds |
| 2       | 1-2 seconds   |
| 3       | 2-4 seconds   |
| 4       | 4-8 seconds   |
| 5       | 8-16 seconds  |
| 6+      | 15-30 seconds |

### Ping

The client sends the signaling service a ping once every `pingFrequency`. If the client does not receive a pong within 15 seconds, it attempts to reconnect.

#### Request

- `jsonrpc`: `2.0`
- `id`: The numeric transaction ID as a string, incremented with each request
- `method`: `System_Ping_v1_0`
- `params`: Empty list

Example:

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "System_Ping_v1_0",
  "params": []
}
```

#### Response

- `jsonrpc`: `2.0`
- `id`: The numeric transaction ID as a string, incremented with each request
- `method`: `System_Pong_v1_0`
- `params`: Empty list

Example:

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "System_Pong_v1_0",
  "params": []
}
```

#### Acknowledgement

- `jsonrpc`: `2.0`
- `id`: The pong transaction ID as a string
- `result`: Empty object

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "result": {}
}
```

### Presence Updated

The signaling service will send the client a message over the websocket when one of the player's friends updates their status.

#### Incoming Message

- `jsonrpc`: `2.0`
- `id`: The numeric transaction ID as a string, incremented with each request
- `method`: `Java_PresenceUpdated_v1_0`
- `params`: Object, or list of objects (only the first is parsed)
	- `profileId`: The player's in-game UUID, without dashes
	- `pmid`: The player's PMID, a UUID used for friend requests, without dashes
	- `status`: One of `ONLINE`, `PLAYING_OFFLINE`, `PLAYING_REALMS`, `PLAYING_SERVER`, `PLAYING_HOSTED_SERVER`, or `OFFLINE`
	- `lastUpdated`: When presence was last updated, in ISO 8601 format

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "Java_PresenceUpdated_v1_0",
  "params": {
    "profileId": "f6489b797a9f49e2980e265a05dbc3af",
    "pmid": "13280211851c4543944889777f191702",
    "status": "PLAYING_SERVER",
    "lastUpdated": "2026-05-20T04:42:00.139151764Z",
  }
}
```

#### Acknowledgement

- `jsonrpc`: `2.0`
- `id`: The presence update transaction ID as a string
- `result`: Empty object

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "result": {}
}
```

## Network Protocol

The client-server authentication/encryption protocol changed drastically. Rather than requiring the client to generate and send an encrypted secret key along with a signed challenge, both client and server use **elliptic-curve Diffie–Hellman** (ECDH) to agree on a shared secret key, then use that key to derive other keys used for encryption, decryption, and integrity.

`version` refers to the [protocol version](https://minecraft.wiki/w/Protocol_version).

### Serverbound Hello

Authentication starts when the client sends the server a `ServerboundHelloPacket`:
- `username`: client's requested username
- `uuid`: client's requested UUID

The server generates an [ECDH curve25519](https://www.rfc-editor.org/info/rfc7748/#section-6.1) private-public keypair ($$K_{S-}, K_{S+}$$). This keypair will be used until `key-rotation-period-seconds` passes. If `key-rotation-period-seconds` is 0, then a new keypair will be generated for each connection.

The server then sends the client a `ClientboundKeyPacket`:
- $$N$$: A random 64-bit nonce
- $$K_{S+}$$: Server public key
- `serverId`: Vanilla always uses "server"
- `auth?`: Whether the client should authenticate with the Session API, true if `online-mode`

### Clientbound Key

The client generates an ECDH curve25519 private-public keypair ($$K_{C-}, K_{C+}$$) of its own, then uses its private key $$K_{C-}$$ and the server's public key $$K_{S+}$$ to compute a shared secret $$S$$.

The client then uses [HKDF-SHA256](https://en.wikipedia.org/wiki/HKDF) to derive several keys from the shared secret $$S$$:
- It first generates a fixed-length key (HKDF-Extract) using the shared secret $$S$$ as the initial keying material (IKM), then adding the nonce $$N$$ and a 24-byte constant as salts.
- Then, it generates four independent derived keys (HKDF-Expand):
	- $$k_{CS}$$: The client to server encryption key (16-byte AES), based on the username, `serverId`, and `version`
	- $$k_{SC}$$: The server to client encryption key (16-byte AES), based on the username, `serverId`, and `version`
	- $$k_A$$: The auth signature (32-byte HMAC-SHA256), based on the username and `serverId`
	- $$k_I$$: The integrity signature (32-byte HMAC-SHA256), based on the username and `serverId`

The derived $$k_A$$ auth signature is used to create the auth digest $$D_A$$, where:
- `|` denotes concatenation
- A single `0x2B` byte is placed between each field

$$ D_A = \text{HMAC-SHA256}(k_A, K_{S+} \:|\: K_{C+}) $$

The derived $$k_I$$ integrity signature is used to create the integrity digest $$D_A$$, where:
- `|` denotes concatenation
- A single `0x2B` byte is placed between each field
- `version` is a big-endian 4-byte integer
- $$N$$ is a big-endian 8-byte integer
- `auth?` is `0x01` if true, `0x02` if false
- `serverId` and `username` are UTF-8 strings

$$ D_I = \text{HMAC-SHA256}(k_I, \text{version} \:|\: N \:|\: \text{auth?} \:|\: \text{serverId} \:|\: K_{S+} \:|\: \text{username} \:|\: K_{C+}) $$

The integrity digest is then used to initialize an AES [initialization vector](https://en.wikipedia.org/wiki/Initialization_vector) (IV):

```java
IVPair generatePair(byte[] seed) {
  Random random = new Random(Arrays.hashCode(seed));
  return new IVPair(random.nextBytes(16), random.nextBytes(16));
}
```

If authentication is enabled, the client POSTs the following information to the Session API's `join` endpoint (currently https://sessionserver.mojang.com/session/minecraft/join):
- `accessToken`: The client's access token
- `selectedProfile`: Player UUID, without dashes
- `serverId`: The auth digest $$D_A$$ truncated to 25 bytes and encoded as [base32hex](https://datatracker.ietf.org/doc/html/rfc4648#section-7), **not** the `serverId` sent from the server to the client

Then, the client sends the server a `ServerboundKeyPacket`:
- $$K_{C+}$$: Client public key
- $$D_I$$: Integrity digest

Future packets are encrypted using AES in [CFB mode](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation#Cipher_feedback_(CFB)), no padding, and initialized with $$IV$$. $$k_{CS}$$ encrypts outgoing packets and $$k_{SC}$$ decrypts incoming packets.

### Serverbound Key

The server uses its private key $$K_{S-}$$ and the client's public key $$K_{C+}$$ to compute the shared secret $$S$$. If the client and server are directly connected to each other without a man-in-the-middle, the server and client shared secrets will be identical.

The server uses $$S$$ to calculate the same derived keys ($$k_{CS}, k_{SC}, k_A, k_I$$), digests ($$D_A, D_I$$), and IV as the client. If the recomputed integrity digest $$D_I$$ does not match the integrity digest sent by the client, login fails with the message "Signature mismatch, potential tampering detected!"

If authentication is enabled, the server POSTs the following information to the Session API's `verify` endpoint (currently `https://sessionserver.mojang.com/session/minecraft/hasJoined`):
- `username`: The username the client requested
- `serverId`: The auth digest $$D_A$$ truncated to 25 bytes and encoded as [base32hex](https://datatracker.ietf.org/doc/html/rfc4648#section-7), **not** the `serverId` sent from the server to the client
- `ip`: IP address of the connecting player, only included if `prevent-proxy-connections` is true

The Session API checks:
- Whether the client's auth digest $$D_A$$ matches the server's $$D_A$$ (to prevent man-in-the-middle attacks)
- Whether the client owns the game
- Whether the client is banned from multiplayer
- If `prevent-proxy-connections` is true, whether the IP address sent indicates a proxy connection

If the client passes validation, the Session API returns the client's profile data, and the client logs into the server with the returned UUID and username.

Future packets are encrypted using AES in [CFB mode](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation#Cipher_feedback_(CFB)), no padding, and initialized with $$IV$$. $$k_{SC}$$ encrypts outgoing packets and $$k_{CS}$$ decrypts incoming packets.

At this point, authentication is complete, and the connection continues to the configuration phase.
